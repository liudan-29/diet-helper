# 去哪吃功能拆解与验收标准

## B1：实体生命周期

### 显性实体

显性实体沿用结构文档中的用餐需求、餐厅快照、推荐结果和用户反馈。

#### 用餐需求

```text
编辑中
  → 已定位
  → 查询中
      → 已返回结果
          → 已选择餐厅
          → 已放弃
      → 无结果
          → 扩大范围后重新查询
      → 查询失败
          → 重试
```

牵连关系：

- 进入查询中时创建高德查询任务。
- 查询成功时生成餐厅快照和推荐结果。
- 查询失败或超时时保留位置、餐次、场景和预算。
- 选择一家餐厅后，未展示的推荐结果标记为过期。
- 重新开始时创建新的用餐需求，旧需求停止追加推荐。

#### 餐厅快照

```text
已创建 → 已标准化 → 已参与筛选
                    → 进入推荐
                    → 被过滤
```

牵连关系：

- 快照只属于一次用餐需求，创建后不修改。
- 高德数据后续变化不回写旧快照。
- 删除用餐需求时，其快照随用餐需求删除。

#### 推荐结果

```text
已生成
  → 被过滤
  → 进入候选
      → 已展示
          → 被跳过
          → 被选择
      → 已过期
```

牵连关系：

- 被选择时，用餐需求进入已选择餐厅。
- 用户换一家时，当前推荐进入被跳过，下一条候选进入已展示。
- 候选数量降到补充阈值时，创建新的高德查询任务，但不重置浏览位置。

#### 用户反馈

```text
已产生 → 已记录
       → 记录失败 → 重试
```

牵连关系：

- 查看、跳过、选择和导航由系统自动产生。
- 不合适原因由用户主动选择。
- 反馈失败不阻塞换一家或打开导航。

### 隐性实体

#### 匿名会话

```text
已创建 → 使用中 → 已过期
```

- 浏览器首次打开产品时创建匿名会话标识。
- 同一浏览器有效期内的用餐需求归入同一匿名会话。
- 会话过期后，历史测试数据保留用于聚合统计，但前端不恢复旧流程。

#### 高德查询任务

```text
已创建 → 查询中 → 已成功
                 → 已失败 → 创建重试任务
                 → 已超时 → 创建重试任务
                 → 已取消
```

- 一次任务只对应一次明确的高德MCP调用。
- 成功任务保存调用参数、完成时间和返回数量，不保存密钥。
- 重试创建新任务并关联原任务，不能覆盖原失败记录。
- 相同用餐需求的重复提交使用幂等标识，避免并发生成重复结果。

#### 推荐规则版本

```text
待启用 → 使用中 → 已停用
```

- 每次用餐需求固定记录一个规则版本。
- 规则更新只影响新需求，旧推荐结果不重新计算。
- 同一时刻只能有一个默认使用的规则版本。

### 不单独建模的内容

- 候选餐厅池由推荐结果的状态表示，不另建重复数据。
- 定位是用餐需求的输入和属性，不另建地点对象。
- 导航是推荐结果的转化动作，不另建导航对象。

## B2：五个必问

### Q1：空状态

- 首次打开时根据时间预选餐次，没有位置时要求定位或手动输入地点。
- 定位被拒绝或浏览器不支持定位时，显示手动地点输入。
- 高德没有返回合适餐厅时，保留原条件并提供修改条件或扩大范围。
- 图片、评分和人均价格缺失时隐藏缺失字段，不显示零值或破图。

### Q2：操作失败

- 网络断开：保留全部输入，恢复网络后允许重试。
- 高德MCP超过8秒：任务标记超时，前端显示重试，不清空条件。
- 高德返回部分无效POI：过滤缺少名称或坐标的数据，其他结果继续参与推荐。
- 反馈记录失败：不阻塞换一家或导航，后续重试。

### Q3：数据被引用

- 参与推荐的餐厅快照创建后不修改。
- 规则更新只影响新需求，旧结果保留原规则版本。
- MVP测试期间保留用餐需求、推荐结果和匿名行为事件。
- MVP不存储姓名、手机号等直接身份信息。

### Q4：并发

- 查询按钮进入加载状态后禁止重复点击。
- 服务端使用用餐需求幂等标识防止重复生成结果。
- 用户修改条件后，以最后一次需求为当前需求，旧查询结果不能覆盖页面。
- 同一需求同时只能有一个候选补充任务。

### Q5：后悔与撤销

- 换一家后允许返回上一家。
- 用户可以返回修改条件，修改后创建新的用餐需求。
- 打开高德前可以改选；外部导航打开后无法撤销。
- 重新开始只把旧需求标记为已放弃，不删除测试数据。

## B3：输入输出链

### 输入

| 来源 | 输入 | 风险与处理 |
|---|---|---|
| 浏览器定位 | 经纬度 | 拒绝、超时或不支持时切换手动地点 |
| 用餐表单 | 餐次、场景、预算、搜索半径 | 前后端都校验范围和枚举值 |
| 服务端环境变量 | 高德Web服务Key | 不存在时使用演示数据，不发送到浏览器 |
| 高德MCP | 周边POI列表 | 超时可重试；缺少名称或坐标的记录丢弃 |

### 输出

| 去向 | 输出 | 风险与处理 |
|---|---|---|
| 推荐页面 | 排序后的餐厅卡片 | 无结果时展示空状态，不伪造真实餐厅 |
| 高德地图 | 目的地坐标和名称 | 只在用户点击后打开外部导航 |
| 本地行为记录 | 查看、跳过和导航事件 | 最多保留最近200条，不阻塞主流程 |
| 测试统计 | 数据来源、结果数量和行为事件 | 演示数据与高德数据必须区分 |

## B4：子功能优先级

### 第一批已实现

1. 浏览器定位与手动地点兜底。
2. 餐次、场景和预算输入。
3. 服务端请求校验。
4. 高德MCP周边搜索客户端。
5. 演示数据回退。
6. 餐厅标准化、硬性筛选和排序。
7. 餐厅卡片、上一家、换一家和高德导航。
8. 查询加载、超时和错误提示。
9. 候选不足时自动扩大范围、补充关键词并去重。

### 第一阶段后续

1. 通过高德地理编码把手动地点转换成真实坐标。
2. 保存用餐需求、餐厅快照和行为事件。
3. 不合适反馈层。
4. 餐厅更多图片和信息层。

## B5：验收标准

### AC-1：用餐需求校验

- 前置：用户提交经纬度、餐次、场景、预算和半径。
- 操作：服务端接收`POST /api/recommendations`。
- 期望：有效输入返回200；无效坐标、餐次、预算或半径返回400和明确错误。

### AC-2：未配置高德Key

- 前置：`AMAP_MCP_KEY`为空。
- 操作：提交有效用餐需求。
- 期望：接口返回200，`mode`为`mock`，至少返回3家可导航演示餐厅。

### AC-3：高德MCP查询

- 前置：配置有效的高德Web服务Key。
- 操作：提交有效用餐需求。
- 期望：服务端连接高德Streamable HTTP MCP，调用周边搜索；Key不出现在前端源码和响应中。

### AC-4：硬性筛选

- 前置：午餐候选包含早餐专营店、已打烊餐厅和正常中餐厅。
- 操作：执行筛选排序。
- 期望：早餐专营店和已打烊餐厅不进入午餐推荐。

### AC-5：定位失败

- 前置：浏览器拒绝定位权限。
- 操作：用户点击定位。
- 期望：定位按钮恢复可用，页面显示手动地点输入，已选餐次、场景和预算不丢失。

### AC-6：重复查询

- 前置：一次查询正在执行。
- 操作：用户再次点击推荐按钮。
- 期望：按钮处于禁用状态，不产生第二次前端请求。

### AC-7：浏览候选

- 前置：接口返回多家餐厅。
- 操作：用户点击换一家后再点击上一家。
- 期望：卡片依次展示下一家和原餐厅，输入条件不变。

### AC-8：导航

- 前置：当前餐厅含有效导航链接。
- 操作：用户点击去这里。
- 期望：新窗口打开高德导航链接，并在本地记录`navigate`事件。

### AC-9：缺失字段

- 前置：餐厅没有图片、评分或人均价格。
- 操作：前端渲染餐厅卡片。
- 期望：使用品类视觉占位，缺失评分和价格不显示零值。

### AC-10：自动化检查

- 操作：执行`npm test`和`npm audit`。
- 期望：全部测试通过，依赖审计为0个已知漏洞。

### AC-11：候选不足自动补充

- 前置：首次1公里搜索经过硬性筛选后少于5家。
- 操作：服务端生成推荐结果。
- 期望：服务端继续用两组补充关键词查询，范围最大扩到2公里和3公里；响应中的`search.expanded`为`true`，`search.usedRadius`为实际最大范围。

### AC-12：候选合并去重

- 前置：三次高德查询包含相同POI，并同时包含已打烊或明显超预算餐厅。
- 操作：服务端合并并排序推荐结果。
- 期望：同一高德POI只返回一次，已打烊和明显超预算餐厅仍被过滤，最终最多返回8家；穷尽查询后不足3家时如实返回现有数量。

### AC-13：真实餐厅照片

- 前置：高德餐厅详情含有效的`photo`或`photos`地址。
- 操作：前端展示餐厅卡并切换到下一家。
- 期望：卡片顶部展示当前餐厅的真实照片，切换餐厅后同步更新；图片缺失、协议无效或加载失败时显示渐变占位图，不出现破图。
